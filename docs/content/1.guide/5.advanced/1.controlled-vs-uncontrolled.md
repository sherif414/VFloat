---
title: Controlled vs Uncontrolled
description: Choose between controlled and uncontrolled open state patterns, with full implementation details.
---

Floating surfaces need to know whether they are visible. In VFloat, that visibility is governed by a standard Vue `Ref<boolean>`.

You have two choices for where that ref lives: let VFloat create and own it internally (uncontrolled), or pass your own ref from the parent component (controlled).

This guide covers both models, how to implement them, and when to use each.

## Uncontrolled: the surface owns itself

In the uncontrolled model, `useFloatingNode` creates and manages its own internal `ref(false)`.

This is the default starting point for most floating interfaces. The component stays small, and your interaction composables coordinate through `node.open`.

Here is an uncontrolled popover:

```vue
<script setup lang="ts">
import { ref } from "vue";
import { useClick, useEscapeKey, useFloatingNode, useOutsideClick } from "v-float";

const anchorEl = ref<HTMLElement | null>(null);
const floatingEl = ref<HTMLElement | null>(null);

// VFloat creates and owns an internal ref(false)
const node = useFloatingNode({
  anchorEl,
  floatingEl,
});

useClick(node);
useOutsideClick(node);
useEscapeKey(node);
</script>

<template>
  <button ref="anchorEl" type="button">Toggle</button>
  <div v-if="node.open.value" ref="floatingEl">Popover content</div>
</template>
```

This model is ideal when:

- The surface lifecycle is self-contained.
- The parent component does not need to read or override the open state.
- Simplicity and minimal boilerplate matter most.

## Controlled: the parent owns the state

In the controlled model, the parent component allocates its own `open` ref and passes it to `useFloatingNode`.

Interaction composables such as `useClick` and `useEscapeKey` still update the state automatically, but the parent now has direct, synchronous access to the boolean ref.

Here is a controlled popover with manual close controls:

```vue
<script setup lang="ts">
import { ref, watch } from "vue";
import { useClick, useEscapeKey, useFloatingNode, useOutsideClick } from "v-float";

const anchorEl = ref<HTMLElement | null>(null);
const floatingEl = ref<HTMLElement | null>(null);

// The parent allocates and owns the ref
const open = ref(false);

const node = useFloatingNode({
  anchorEl,
  floatingEl,
  open,
});

useClick(node);
useOutsideClick(node);
useEscapeKey(node);

// React to state changes with standard Vue watchers
watch(open, (isOpen) => {
  if (isOpen) {
    // Perform side effects when the surface opens
  }
});

// Update state programmatically
function closeSurface() {
  open.value = false;
}
</script>

<template>
  <button ref="anchorEl" type="button">Toggle</button>
  <div v-if="open" ref="floatingEl">
    <p>Controlled content</p>
    <button type="button" @click="closeSurface">Close</button>
  </div>
</template>
```

Because `node.open` points to your `open` ref, mutating either `open.value` or `node.open.value` immediately triggers Vue reactivity.

::warning
The `open` ref passed to `useFloatingNode` must be a synchronously mutable `Ref<boolean>`. Avoid passing read-only refs or computed properties with deferred setters, as asynchronous or delayed mutations cause visual lag between user interactions and DOM updates.
::

## Closing nested surfaces programmatically

Closing a parent node does not automatically cascade to its open descendants.

When you need an explicit parent teardown that dismisses an entire branch of nested menus or sub-dialogs, walk open descendants using `node.traverse` with bottom-up ordering:

```ts
function closeAll() {
  node.traverse(
    (descendant) => {
      descendant.open.value = false;
    },
    { order: "bottom-up" },
  );
  node.open.value = false;
}
```

Visiting children bottom-up ensures inner cleanup hooks and return-focus restorations run before the root container unmounts.

## When each model makes sense

Use the uncontrolled model when:

- The floating surface is a local UI utility (simple tooltips, standalone popovers).
- No external code needs to force the surface open or closed.
- You want the cleanest and most compact script block.

Use the controlled model when:

- Another system needs to control visibility (URL routing, query parameters, multistep wizards).
- Opening or closing the surface must synchronize with other application state (such as resetting a form on dismiss).
- Multiple floating surfaces coordinate so that opening one surface closes another.

## Keep one node per surface

Whatever state model you choose, every interaction composable for a given floating surface must share the same `node`.

That shared `node` is what allows `useClick`, `useEscapeKey`, `useOutsideClick`, and positioning to cooperate seamlessly rather than conflicting over state transitions.
